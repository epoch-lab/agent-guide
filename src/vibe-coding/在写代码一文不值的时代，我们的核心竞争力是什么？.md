# 在写代码一文不值的时代，我们的核心竞争力是什么？

- 核心竞争力是：设计并构建复杂系统、做架构、做验收。

## 一套可执行的流程

1. Brainstorm：头脑风暴，讨论要做什么。
2. Map：根据头脑风暴产出 PRD，拆解为 Epic 和 Story。
3. Act：循环处理这些 Epic 和 Story。

- 确认系统健壮性，做验收的能力。
- 用多个 AI 进行“打架”：一个 Claude Code 写代码，一个 Codex 找 Bug，再由人判断哪些是误报，哪些是真 Bug。

## 设计

核心是不能凭感觉写代码，也不能一点点让 AI 来“磨”代码，否则很难做出连续、可持续、可维护的系统。

你应该让想法（Idea）对应到具体的 Spec，再对应到具体代码。每行代码都要有迹可循。出问题时，再精准修改。

### 1) 饱和式防御（Adversarial Review）——左手互搏

不要只让 AI 写代码，要让 AI 互相对抗。这是最烧 Token、但能保证系统健壮性的方法。

传统模式（省 Token）：

> 你：“写一个登录函数。”
>
> AI：“好的，代码如下……”（结束）

烧 Token 模式（Agent Workflow）：

- Agent A（Builder）：写出登录函数。
- Agent B（Hacker）：模拟攻击这段代码，尝试 SQL 注入、XSS、并发竞争条件，并生成攻击报告。
- Agent C（Auditor）：根据 B 的报告指出 A 的漏洞，并要求 A 重写。
- Loop：A 重写 -> B 再攻击 -> C 再审核，直到 B 找不到漏洞。

怎么做：

- 在 AGENTS.md 里，把 Auditor 的职责定义为“烧 Token”。
- 要求它对每一行代码做“有罪推定”，强制多轮推理循环，直到代码达到要求。

### 2) 极端详尽的规格说明（Hyper-Specification）——文档即源码

把 Token 烧在“理解”和“设计”上，而不是“实现”上。

传统模式：

- 脑子里有个模糊想法，边写代码边想细节。

烧 Token 模式：

- 先写一个 spec.md。
- 交给 AI：“作为架构师，请用 5000 个 Token 推演这个设计的边缘情况（Edge Cases）。如果网络断了怎么办？如果数据库锁了怎么办？如果用户输入了 emoji 怎么办？”
- 让 AI 把文档扩充成一份滴水不漏的施工图纸。

代码生成只是一瞬间的事，但前面的推演过程会消耗大量 Token。

怎么做：

- 按 AGENTS.md 的流程走：Idea -> System Design -> Spec -> Code。
- 在 Spec 阶段，强迫 AI 做充分推理，把可能出错的地方先想一遍。

### 3) 语义级索引与重构（Semantic Refactoring）——知识图谱化

维护旧代码是程序员最头疼的事。未来的维护方式是让 AI 吃透整个项目。

传统模式：

- 用 Ctrl+F 搜变量名，靠人脑记忆代码逻辑。

烧 Token 模式：

- 每次提交前，把整个项目上下文（几万甚至几十万 Token）交给 AI。
- 指令示例：“结合整个项目架构，分析这次修改 User.ts 会不会影响 Order.ts，并生成影响范围报告。”
- 甚至让 AI 自动生成并维护实时 Wiki（就像 Repo Guide 要做的事）。

怎么做：

- 利用长上下文模型（如 Gemini 1.5 Pro、Claude 3.5）。
- 不要吝啬 Context Window，把相关的 50 个文件都塞进去，让 AI 拥有上帝视角。

### 4) 测试驱动开发（TDD）的极致版——自动生成测试山

测试代码通常比业务代码多。人懒得写测试，但 AI 不累。

烧 Token 模式：

- 业务代码写完后，指令：“为这个函数生成 20 个测试用例，覆盖正常情况、边界情况、错误输入、性能压力测试。”
- 再指令：“运行这些测试。如果失败，自动修复代码，直到测试全部通过。”

## 总结：你的核心竞争力变了

以前，你的竞争力是“我知道怎么写这个算法，能省几行代码”。

未来，你的竞争力是“我知道怎么设计一套 Workflow，让 AI 消耗 100 万 Token，帮我完成原本需要 5 人团队一周的工作”。

最烧 Token 的事情，就是把 AI 当作廉价的高级劳动力，去穷举、去对抗、去验证、去推演。

这就像以前盖房子要省砖头（算力）；现在砖头不要钱了，你要做的是用无数砖头去测试承重，直到盖出最稳固的大楼。
